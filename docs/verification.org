#+title: SIR Verification
#+author: Aryadev Chavali
#+date: 2026-10-16

This is the working docket for verification after lowering.  The implemented
compiler contract is in [[file:compiler.org]].  This document records current
design direction and questions to exercise during implementation; move durable
rules to the compiler document only after they survive code and tests.
* Aim
Verify the types and stack effects of SIR instructions, blocks, and bodies;
report useful source-backed errors; and retain inferred facts for evaluation,
optimisation, and later backends.  First check SIR structure so inference can
index it safely.

A successful derivation establishes the properties expressed by the chosen
type algebra.  It does not establish that a program terminates or produces its
intended answer.  The initial scope of the algebra and the treatment of valid
programs outside it remain implementation questions.
* Working algebra
** Values and stack effects
- Represent stack effects with typed input and output rows.  A row variable
  permits a body to use an unknown prefix: ~rho A B -> rho B A~ describes a
  reusable swap.  ~()~ denotes the exactly empty stack sequence, not a value.
  Thus ~A -> ()~ describes a closed one-input drop, while a reusable drop has
  effect ~rho A -> rho~.
- Keep a value's type distinct from the effect of calling that value.  A
  closure type contains the effect of its body.  ~Load~ pushes the referenced
  value, including a closure or primitive; it does not assert that the value is
  inert.  ~Call~ applies the runtime dispatch effect: execute a closure or
  primitive, or push an inert value.
- A target may hold several kinds of value.  Prove a ~Call~ safe only when
  every possible kind has a compatible effect at that site.  For example,
  =examples/bigrange-vec.rfp= binds ~acc~ first to ~[0 vmake]~ and later to a
  vector.  Both calls can have effect ~rho -> rho Vector~ although the value
  types differ.  Preserve this program before considering an optimisation
  that changes a definitely inert ~Call~ into a ~Load~.
- Primitive effects and runtime-variable value types belong in their
  registries, which currently contain names only.  Start with contracts whose
  runtime meaning is clear.  Do not silently give an uncontracted primitive a
  polymorphic effect: that would claim safety that has not been proved.

These are requirements on the first useful model, not a commitment to a
particular Rust representation for rows, alternatives, or schemes.
** Constraints and resolution
Instructions, block edges, and body boundaries generate equations in one
shared constraint system.  Their variables cross those boundaries through
locals, captures, calls, and recursion; independent solvers for each level
would have to reproduce the same relationships.  Implement only the solver
operations needed by exercised cases, but make constraint provenance
available for diagnostics.

Unifying unknown type variables is different from combining possible runtime
values.  At a join, retain the alternatives needed to check later calls.  Do
not select one executable or inert alternative merely because it makes the
equations solvable.  Effects at joins must respect the agreed stack discipline:
ordinary conditional paths need compatible stack results, including height.

A recursive closure with result effect ~I -> O~ gives its raw body a self value
of type ~Closure(I -> O)~ alongside input ~I~; the raw body must produce ~O~.
Exercise the actual SIR stack order and capture layout before fixing this rule
in code.  Decide how polymorphic effects are generalised and instantiated at
call sites, and make recursive solving terminate or report its limit.
* Outcomes and diagnostics
- A contradictory constraint is a type or stack error.  An annotation cannot
  make the contradiction valid.
- An underdetermined constraint means inference lacks information needed to
  establish a required effect.  Verification fails with a diagnostic naming
  the missing fact and its source location.  A future user ascription may add
  the needed constraint, but no ascription syntax is required for the first
  verifier.  Unconstrained variables that can be safely generalised are not
  failures of inference.
- A program may need an effect the current algebra cannot express, or solving
  may reach a documented limit.  Verification fails and reports that limit
  honestly.  Do not suggest an ascription unless the proposed type language
  can express the effect.
- Malformed SIR is a compiler bug, not a user type error.  Stop analyses that
  would rely on its invalid structure.

The first verifier accepts only programs for which it establishes the required
effects.  A future dynamic boundary would be a separate language decision,
with its own guarantees for later phases; it must never make an unproved
effect look proved.
* Milestones
** 1. Establish contracts and structural checks
- Confirm the runtime meaning of ~PushData~, ~Load~, ~Call~, ~Bind~,
  ~MakeClosure~, recursive entry, and terminators against source, tests, and
  selected reference-interpreter cases when that settles semantics.
- Define the first value types, stack rows, effects, and primitive/variable
  contracts.  Cover known data, closures, and the primitives needed by the
  first inference examples.
- Validate module, datum, body, block, local, capture, primitive, and variable
  IDs before indexing them.  Check instruction/origin cardinality, syntax
  origins, entry blocks, closure references, and branch/jump destinations.
  Derive lexical parents from closure creation before checking capture sources.
- Check reachability.  Invalid generated SIR should yield a compiler-bug
  diagnostic, not a panic.

This milestone leaves a structurally safe input and explicit contracts for
the first inference rules.
** 2. Infer instruction effects
- Generate stack and value constraints for ~PushData~, ~Load~, ~Bind~, and
  ~MakeClosure~.  Track types attached to local and capture slots, including
  the relationship between a capture and its source.
- Generate dispatch constraints for ~Call~ from its target's possible values.
  Test direct primitive calls, known inert values, known closures, and calls
  through locals and captures.  Keep the value type and call effect separate.
- Build minimal row/type unification alongside these rules.  Preserve source
  origins so a failed equation can identify the relevant instruction and
  earlier requirement.

This milestone ends with straight-line body effects and focused mismatch and
underflow diagnostics.  A reusable body may acquire input requirements;
the entry body is checked against its actual initial stack.
** 3. Infer block and control-flow effects
- Compose instruction effects in execution order.  ~End~ constrains a body
  output; ~Jump~ passes its exit state to a successor; ~Branch~ consumes a
  condition and passes the remaining state to both successors.
- Reconcile states at joins without losing possible value kinds.  Require
  compatible outputs from reachable exits of one body.  Test direct arm
  termination, shared continuation blocks, repeated predecessors, and
  unreachable blocks.
- Check definite local initialization on every reachable path.  An arm-local
  binding must not become available after a join unless every path defines it.
- Solve CFG cycles to a fixed point or report a defined solver limit.  Keep
  value-flow joins and type-variable unification conceptually separate.

This milestone ends with an inferred effect for non-recursive multi-block
bodies and facts at block entries and exits.
** 4. Infer body and closure effects
- Connect each body's entry and reachable exits to one body effect.  Relate
  ordinary closure values to their bodies, and captures to enclosing slots.
- Add recursive closure equations.  Test calls through ~self~, mutually
  dependent facts across blocks, and closure calls whose effects are
  instantiated at multiple sites.
- Establish generalisation, instantiation, occurs-check, and termination
  behaviour using concrete examples before promising principal types for all
  bodies.  In particular, test =examples/bigrange-vec.rfp= and higher-order
  combinators.  Use =examples/combinators.rfp= to examine programs whose
  effects may exceed a finite-row algebra.

This milestone ends with explicit solved effects or a specific, honest
failure result for each analysed body.
** 5. Expose and integrate verification results
- Return diagnostics and reusable type/effect facts keyed to SIR sites.  Use
  body and block IDs plus an instruction position or dedicated instruction ID
  only when consumers show which identity is needed.  Keep this data separate
  from executable SIR instructions.
- Add the verification gate after lowering.  Errors, including unresolved
  required effects, prevent evaluation or backend consumption.  Run the
  example corpus and ~./scripts/verify~.
- Once the algebra and diagnostics are useful, review failures caused by
  insufficient information.  Add value ascription syntax only if it resolves
  real cases worth supporting.  Treat an ascription as an additional checked
  constraint, not as a replacement for verification.

If introduced, a postfix value ascription can constrain a raw closure before
~rec~, its recursive result after ~rec~, or both.  The recursive closure rule
relates those sites, so neither annotation needs to be copied onto the other.
Recognition of ~rec~ and ~if~ must see through ascriptions while preserving
their equations.  Decide the syntax and SIR side-map anchors during that work.
* Cases that should drive decisions
- ~[$x]~ has an open-stack drop effect.  An empty result row ~()~ has its
  exact-stack meaning only when the input is closed too.
- =examples/bigrange-vec.rfp= must preserve the mixed ~acc~ call described
  above.  A later proven-inert-call optimisation must preserve its semantics.
- Branches with incompatible stack heights expose the chosen conditional
  discipline; branches with different value kinds expose the join model.
- Recursive and higher-order examples exercise effect instantiation and
  solver termination.  If a working program has no effect in the chosen
  algebra, classify it as an expressiveness limit rather than missing data.
- Tests should distinguish contradictions, insufficient information,
  unexpressible effects, solver limits, and malformed SIR.
* Questions to settle during implementation
- What value alternatives are needed to verify mixed dispatch without
  exponential growth?  Which conditions are cheap enough to resolve during
  verification?
- Which primitive contracts need value-dependent or alternative effects,
  especially ~cswap~ and dynamic ~if~?  What are the runtime contracts for
  the three primordial variables?
- Where may a polymorphic closure effect be generalised, and how do recursive
  uses instantiate it?  What restriction makes solving terminate?
- Which example programs fall outside the initial algebra, and does their
  rejection reveal a type-language feature worth adding before the driver
  gate?
- Which inferred facts do evaluation and optimisation actually need, and
  what SIR-site identity keeps those facts stable enough for those consumers?
