* PROJ IR compiler first pass :compiler:
** Preamble
We now want to make the program a compiler for the `rForsp` language.
Currently the program is a very simple interpreter: read -> compute ->
stop.  The AST that we read is basically 1-1 with what we evaluate,
which is nice for simplicity's sake, but isn't so nice for a genuine
compiler - the amount of nesting works directly counter to our ability
to optimise.

rForsp is, with the exclusion of environments, quite a flat language
itself:
- Bodies of code are implemented as flat buffers (vectors).
- nested function calls are simply adjacent words in the same vector
  i.e. ~f(g(h(x)))~ is ~[x h g f]~
- Operator precedence is a non-issue.

The pain points with compiling rForsp, which weren't painful when we
just concerned ourselves with interpreting, is that a lot of stuff is
implicit in its construction:
- ~1~ really represents "Push the integer 1 onto the value stack".
- ~$x~ means bind the symbol "x" in the current environment with
  whatever value is on the stack.
- ~f~ means lookup the symbol "f" in the current environment, then
  compute the result of it.

A flatter representation that makes these more explicit, in trade of
being more verbose, would allow us to reason about rForsp code more
effectively:
- Easier to evaluate since:
  - Each operation is explicit; we don't need to wait for the
    evaluator to figure it out when iterating but already have
    dedicated handles for each operation.
  - We're not jumping between different chunks of memory, but the same
    overall block.
- Easier to optimise, since we can perform static analysis on the code
  ahead of time.

The first attempt of the IR compiler will do the following passes:
- Convert source text to a High-Level IR (HIR) that preserves nesting,
  etc (analogous to the old interpreter homoiconic object model).
- Perform resolution and analysis to lower this HIR to a Semantic
  Stack-Effect oriented IR (SIR).
- Pass the SIR into a temporary evaluator.

* BACKLOG GC :gc:
** BACKLOG Better slot pools :bibop:
The current GC manages a single pool of fixed 16-byte slots, used for
pairs, closures, and vec metadata (the ~vec_t~ header).  Vec ~items~
buffers are ~calloc~/~realloc~/~free~'d via libc, which fragments the
heap and requires the ~vec_bits~ special case in sweep/stop.

Proposal: BiBOP (Big Bag of Pages).  Multiple pools, each with a
different slot size corresponding to a power-of-two number of ~obj_t*~
pointers (4, 8, 16, 32, ... 512).  The ~vec_t~ header stays in the
existing 16-byte pool (tagged ~TAG_VEC~ as before), but ~vec_push~
allocates the ~items~ buffer from the pool whose slot size best fits
the requested capacity.  On resize (doubling), the old ~items~ buffer
is immediately returned to its pool's free list and the new one
allocated from the next size up.

Pools beyond 512 slots (or any missing size class) fall back to a
managed ~malloc~ with an inline header (~size~ + ~mark bit~) so the GC
can still trace and reclaim them uniformly.

Benefits:
- No ~calloc~/~realloc~/~free~ for common vec sizes, so fewer libc
  calls, better locality, lower fragmentation.
- Immediate reuse on resize: old buffer goes straight to free list
  instead of waiting for a GC cycle.
- Pool memory is contiguous and page-aligned, so we have more
  cache-friendly GC scans.

Questions:
- How to find the sized-pool slot from an ~items~ pointer during GC
  mark?  Copying ~mimalloc~, we could align the chunk such that the
  header is at the base of the region boundary - then, we just need to
  clear off the lower N bits of the specific pointer to get the top of
  the chunk.
- Chunk layout for sized pools: a 32-byte-slot chunk has half the
  slots per chunk vs a 16-byte one.  Do we keep ~GC_CHUNK_SLOTS~ fixed
  (variable chunk size) or fixed chunk size (variable slots per
  chunk)?  Fixed chunk size is simpler for address arithmetic.
- The existing ~gc_find_chunk~ already linear-searches for meta-pool
  chunks.  Adding N more pools to search multiplies the cost
  proportionally.  Worth bundling with the [[*Better ~gc_find_chunk~]]
  work.

*** BACKLOG GC mark integration
In ~gc_mark_obj~, when marking a ~TAG_VEC~ slot, locate its ~items~
buffer in the sized pools and ensure we mark the reachable pointers
appropriately.
*** BACKLOG GC sweep integration
We'll have to iterate through not only the 2 object slot pool, but
also all the other sized pools.  Each pool gets its own free list.
Malloc-fallback blocks use the inline header, and ~gc_t~ should have a
free list dedicated to just those.
*** BACKLOG GC collect
We still only need to concern ourselves with the 2 object slot pool -
vector metadata will always lie there.  So our general choice of
objects to mark will be the same still.
