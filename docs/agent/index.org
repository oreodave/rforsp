This is the shared map of the documentation.  It is not the entry
point: read your role document first, then return here.
* Role documents
Every session is either a builder session or an architect session.
The role document sets purpose, scope, reading order, and write
permissions; this document only describes the terrain they operate on.

- [[file:builder.org]] - concrete code, implementation review, full
  repository access.
- [[file:architect.org]] - design, specification, and argument.
  Documents only.

If you have arrived here without having read one of the two, stop and
ask which role applies.  The documents below are read and written
differently by each, and guessing wrong corrupts state.
* Link conventions
All links, unless explicitly specified, are _relative_ links to the
document being read/generated.  For example,
[[file:../../src/main.rs]] points to the ~main.rs~ file in
=<root>/src/main.rs=, and is relative to this current document which
is in =<root>/docs/agent/index.org=.
* Documents
The documentation is tiered by how fast it changes and by what
authorises a change to it.
** Specification
Slow-moving, authoritative, changed only by review.  No agent amends
these unprompted.
1) [[file:../summary.org]] - a basic summary of the language.
2) [[file:ir-design.org]] - the authoritative design of the
   compilation phases, IRs, and diagnostics.  This is the document to
   consult when unsure what a phase should do or report.
** Rationale
Append-only, preserved across sessions, never regenerated.  These
record the tradeoffs and rejected alternatives that the code cannot
show - the *why* behind the shape of things.
1) [[file:logs/architect.org]] - design decisions and their
   rationale.  Written by the architect.
2) [[file:logs/builder.org]] - implementation decisions and their
   rationale.  Written by the builder.
** Working state
Mutable, expected to go stale, rewritten rather than accumulated.
1) [[file:status.org]] - the current, quickly-obsolescing state:
   repository layout, build status, completed and pending milestones,
   in-flight work, and suggested next steps.  It derives entirely
   from the code, git history, and test runs, and is regenerated by
   the builder at handover.
2) [[file:questions.org]] - open design questions, each with what
   would settle it and what it blocks.  Entries are added by either
   role and removed only by the architect, on resolution, with the
   resolution recorded in the architect log.
* Handover
The handover procedure is role-specific and is defined in
[[file:builder.org]] and [[file:architect.org]].  Two rules hold for
both:
- Logs are append-only.  Never regenerate one, never edit an existing
  entry, never summarise a log in place.
- Working state is rewritten, not appended.  =status.org= is
  regenerated wholesale; =questions.org= has entries added and
  removed.

A decision that was reached but not written down did not happen.  The
session ends and the context is gone; the repository is the only
thing that persists.
* Document guidelines
When generating an ~org~ document, please ensure these guidelines
(along with presumed ones from reading other ~*.org~ documents) are
followed:
- Wrap lines on the 70 fill column but aggressively; see [1]
  - Within a block you are permitted to go way past the fill column
- No newlines after headings and before them - make it tight.
- Newlines after blocks (i.e. ~#+begin_src/#+end_src~) is fine, but if
  a sentence precedes a block and has a colon, close the gap (see [2])

[1]: Aggressive wrapping example
#+begin_src diff
- A ~LoadRef~ resolving to a primitive pushes the primitive value; it does
- not execute the operation.
+ A ~LoadRef~ resolving to a primitive pushes the primitive value; it
+ does not execute the operation.
#+end_src

[2]: Block newlines guide
Since the sentence preceding the block has a colon, remove the
newline:
#+begin_example
The conditional is written:
#+begin_src text
cond [then] [else] if
#+end_src
#+end_example

... but if the preceding sentence doesn't have a colon, don't:
#+begin_example
Capture slots contain values, not mutable binding cells. A captured
vector is still an aliased heap reference, so vector-based boxing
works without mutable lexical bindings.

#+begin_src text
CaptureSource = LOCAL(LocalId)
              | CAPTURED(CaptureId)
              | PRIMITIVE(PrimitiveId)
CapturePlan = Vec<CaptureSource>
#+end_src
#+end_example

Always have a newline after blocks.
