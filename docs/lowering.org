#+title: Phase 4 Lowering Work List
#+author: Aryadev Chavali
#+date: 2026-09-30

This is the disposable work list for lowering.  It records the next concrete
steps and open decisions while the phase is being implemented.  Update
[[file:compiler.org]] with behaviour that survives implementation, then delete
this file when lowering is complete.
* Scope
Lowering consumes successfully resolved HIR and produces the first executable
compiler IR.  This phase should make the meaning already established by HIR
and resolution explicit without repeating name lookup or frame-layout work.

Lowering must cover every current HIR form, resolution entry, and reference
target.  In particular, runtime variables are part of the implemented
resolution interface and cannot be omitted merely because the speculative IR
design predates them.

This phase does not include structural verification, execution, effect
inference, optimisation, or a final native-code ABI.  Avoid settling those
later phases beyond what lowering itself requires.
* Constraints carried from implemented phases
- The driver invokes lowering only after resolution succeeds.  A poison entry
  reaching lowering is a compiler invariant failure, not a user diagnostic.
- Source origins remain available through each form's ~SyntaxId~.  Lowered
  operations retain enough origin information for later diagnostics and logs.
- Binding identities, local slots, body layouts, and capture order come from
  resolution.  Lowering does not derive a second version of them.
- Lists and quoted forms are data.  Lowering does not resolve or execute their
  contents.
- Ordinary vectors create bodies.  Recognised conditional arms belong to the
  enclosing body rather than creating closures.
- Conditional-arm locals use the enclosing body layout while their names remain
  arm-local.
- Deeply nested input remains attacker-controlled.  Lowering must not require
  recursive host-stack traversal.
* Open decisions
Resolve each decision when its first implementation milestone needs it.
- What is the smallest IR that represents the operations emitted by current
  HIR and resolution, without encoding verifier or evaluator policy?
- How are quoted forms, lists, integers, symbols, and quoted vectors represented
  as runtime data owned by the lowered result?
- How do load and call operations distinguish locals, captures, primitives, and
  runtime variables?
- How are bodies and control-flow regions identified and stored?
- Which operations end a body or control-flow region, and when does a call need
  explicit tail position?
- Does constant interning earn its complexity in the first implementation, or
  should every datum receive an independent entry?
* Milestones
** TODO 1. Establish the lowering boundary
Define the phase's input and output at the module boundary and add the empty
entry-body case.

The initial result needs enough structure to identify the entry body and retain
source origins.  Keep construction APIs private until tests demonstrate what
later phases need to inspect.

*Done when* an empty resolved program lowers successfully, the result has one
entry body, and malformed synthetic input fails as a compiler invariant rather
than a user-facing diagnostic.
** TODO 2. Lower data and straight-line entry forms
Implement lowering for integers, quotes, and lists, including nested datum
content.  Establish the owned data representation needed by those forms.

Then lower top-level binds, loads, and calls using the binding and target
information produced by resolution.  Cover local, primitive, and runtime
variable targets before introducing nested bodies.

*Done when* straight-line programs without vectors lower form-for-form with the
expected origins, local slots, and reference targets.
** TODO 3. Lower ordinary closures
Create lowered bodies for vectors resolved as ordinary closures.  Transfer each
body's local count and capture layout directly from resolution, then emit the
operation that constructs the closure in its enclosing body.

Exercise direct captures, repeated captures, and captures forwarded through
several nested bodies.  Lower references inside the nested body against its
local and capture slots rather than global binding identities.

*Done when* nested closures preserve resolution's body layouts and capture
ordering, including transitive captures.
** TODO 4. Lower recognised recursion
Handle vectors resolved as recursive closures and consume the paired recognised
~rec~ form exactly once.  Keep dynamic calls to a shadowed or computed ~rec~ on
the ordinary call path.

Add invariant checks for impossible pairings between the recursive operand and
operator entries.

*Done when* recognised recursive closures differ from ordinary closures in the
lowered result, while dynamic ~rec~ calls remain ordinary references.
** TODO 5. Lower recognised conditionals
Introduce the control-flow representation required by recognised ~if~ forms.
Lower vector arms into regions of the enclosing body, preserving their arm
roles, origins, and shared local layout.

Support both a conditional followed by more forms and a conditional at the end
of a body.  Decide continuation and tail-position rules from these cases rather
than importing the speculative design unchanged.

*Done when* both arms reach the correct continuation, arm-local bindings cannot
leak into the continuation, and nested conditionals lower without closure
allocation for recognised arms.
** TODO 6. Complete call and termination handling
Determine tail position from the control flow implemented in the previous
milestone.  Represent body completion and any tail calls explicitly enough for
the next phase to verify them.

Cover calls to locals, captures, primitives, and runtime variables in ordinary
and tail positions.  Do not attach stack-effect or runtime-dispatch machinery
that lowering does not need.

*Done when* every path through every lowered body has an explicit end or
transfer, and calls in tail position are distinguishable without inspecting
HIR again.
** TODO 7. Harden traversal and invariants
Make lowering iterative across deeply nested bodies and datum trees.  Audit all
HIR, ~Resolution~, and ~Target~ variants so additions cause an obvious compile
failure or invariant failure rather than silent omission.

Add focused tests for source-origin alignment, body and target identifiers,
layout bounds, branch structure, and invalid synthetic combinations.  Use
small source programs for semantic cases and direct construction only for
unreachable invariant failures.

*Done when* deep nesting tests pass, every current variant has coverage, and
lowered output can be inspected without consulting discarded traversal state.
** TODO 8. Integrate and close the phase
Wire lowering into the compiler driver after the resolution gate.  Add a log
stage that gives useful deterministic output for tests and manual inspection.
Run the example corpus through lowering and add end-to-end coverage for multiple
sources and the embedded standard library.

Record the implemented lowering interface and durable invariants in
[[file:compiler.org]].  Remove speculative detail that implementation disproves
only from current documentation; preserve the archived exploration as history.

*Done when* ~./scripts/verify~ exercises lowering for the compiler examples,
the driver cannot report success without producing lowered output, and this
work-list file can be deleted.
